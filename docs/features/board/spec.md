# Spec — board

> **Glossary:** [CONTEXT](../../../CONTEXT.md)
> **Reference module / docs / channels used:** None — only the interview + CONTEXT. Upstream input: `docs/idea-brief.md` (confirmed idea, Approach C), `docs/architecture-map.md` (current repo state).

## 1. Context

Маленькі команди 3–7 людей хочуть показувати стан своєї роботи людям поза командою — стейкхолдеру, замовнику, аудиторії воркшопу — не змушуючи їх реєструватись заради одного перегляду. Наявні канбан-інструменти або ховають перегляд за лімітом учасників безкоштовного плану (Trello: 10 людей на workspace, далі всі борди стають read-only для всіх), або взагалі не розділяють «редагувати» й «дивитись» — хто має посилання, той і редагує.

Найближчий воркшоп — фіксований дедлайн і водночас перевірка продукту наживо: аудиторія (перша хвиля — близько 30 людей) має відкрити публічний лінк зі своїх телефонів і побачити, що задачі реально рухаються, а не що це макет слайда.

Продукт — рівно одна board, яку team member редагує напряму (створює, редагує, переміщує перетягуванням, видаляє task), і яку будь-хто може відкрити через один public link виключно на перегляд, без реєстрації. Стан зберігається централізовано, тому board переживає і чистку браузера власника, і сам воркшоп, а viewer завжди бачить актуальний стан при кожному відкритті лінка.

Репо наразі — чистий full-stack скафолд (`docs/architecture-map.md`): існує лише auth/user-каркас із наявним механізмом автентифікації, продуктових доменних модулів ще нема. Board — перший продуктовий модуль, і він свідомо не використовує наявну автентифікацію — team member працює без входу в систему, а public link обходить її повністю (`docs/architecture-map.md` §Constraints & known tech-debt).

## 2. Goals

- Дати малій команді спільний, завжди актуальний стан задач без будь-якої реєстрації чи налаштування облікових записів.
- Дати команді один лінк, яким можна довести реальний прогрес глядачам ззовні — лінк завжди показує поточний стан і ніколи не дає права редагування.
- Тримати весь продукт в межах однієї board без додаткових екранів чи режимів — без спринтів, оцінок, кількох дощок чи навігації між ними.

## 3. Non-goals

- Спринти, ітерації, бурндауни, оцінки (story points, години, велосіті) — навмисно виключені, щоб інструмент лишався зрозумілим за хвилини, а не перетворювався на систему управління проєктами.
- Кілька дощок і навігація між ними — продукт це рівно одна board; підтримка кількох потребувала б окремого екрану вибору борди, якого команда не просила.
- Реєстрація, вхід, ролі та права доступу всередині команди — прибирає найбільший клас складності (сесії, відновлення паролю, керування правами) і відповідає прямій вимозі користувача.
- Редагування гостями за публічним лінком — read-only і є тим, що робить лінк безпечним для поширення; якби гість міг редагувати, той самий лінк, що витік у чужі руки, ставав би ризиком вандалізму, а не лише витоку інформації.

## 4. User stories

### US-01: Створити задачу

**As a** team member
**I want** додати нову task із назвою на board
**So that** нова робота стає видимою для всієї команди й глядачів

### US-02: Відредагувати задачу

**As a** team member
**I want** змінити текст або виконавця вже створеної task
**So that** я можу виправити помилку без видалення й повторного створення task

### US-03: Перемістити задачу перетягуванням

**As a** team member
**I want** перетягнути task в іншу column
**So that** статус задачі на board відповідає реальному стану роботи

### US-04: Видалити задачу

**As a** team member
**I want** прибрати task з board
**So that** застарілі або тестові задачі не лишаються видимими для глядачів

### US-05: Отримати публічний лінк

**As a** team member
**I want** отримати public link на board
**So that** я можу показати реальний стан роботи людям поза командою без запрошення їх у команду

### US-06: Відкликати публічний лінк

**As a** team member
**I want** відкликати чинний public link
**So that** я можу зупинити доступ ззовні, коли більше не хочу ділитись board

### US-07: Переглянути дошку за публічним лінком

**As a** viewer
**I want** відкрити board за public link і побачити її поточний стан
**So that** я бачу, що робота реально рухається, не приєднуючись до команди

## 5. Acceptance criteria

### AC-01 (US-01) — happy path

**Given** team member дивиться на board
**When** team member додає нову task із непорожньою назвою
**Then** система створює task у найлівішій column і одразу показує її там

### AC-02 (US-01) — error

**Given** team member створює нову task
**When** team member намагається зберегти task із порожньою назвою
**Then** система блокує створення й повідомляє team member, що назва task обов'язкова

### AC-03 (US-02) — happy path

**Given** team member володіє вже створеною task
**When** team member змінює її назву або виконавця і зберігає
**Then** система записує нові значення й одразу показує їх на board

### AC-04 (US-03) — happy path

**Given** team member бачить task в одній column
**When** team member перетягує цю task в іншу column
**Then** система записує нову column як поточний статус task і показує task саме там

### AC-05 (US-03) — domain invariant

**Given** team member перетягує task
**When** team member відпускає task поза межами будь-якої дійсної column
**Then** система лишає task у попередній column без змін, ніби перетягування не відбувалось

### AC-05b (US-03) — domain invariant (concurrent edge)

**Given** двоє team member одночасно перетягують ту саму task у різні column
**When** обидві зміни доходять до системи
**Then** система лишає task рівно в одній column — тій, чия зміна оброблена останньою — і кожен наступний перегляд будь-ким показує саме цей єдиний узгоджений стан

### AC-06 (US-04) — happy path

**Given** team member бачить task на board
**When** team member видаляє цю task
**Then** система прибирає task з board, і вона більше не показується нікому

### AC-07 (US-05) — happy path

**Given** team member працює з board, у якої ще немає активного публічного лінка
**When** team member запитує public link
**Then** система видає team member лінк, що завжди показує поточний стан board лише на перегляд

### AC-08 (US-06) — happy path

**Given** team member має чинний public link
**When** team member відкликає цей лінк
**Then** система припиняє показувати стан board за цим лінком

### AC-09 (US-07) — happy path

**Given** viewer має чинний public link
**When** viewer відкриває цей лінк
**Then** система показує viewer поточний стан board з усіма column і task, доступний лише на перегляд

### AC-10 (US-07) — authorization

**Given** viewer переглядає board за public link
**When** viewer намагається перетягнути, відредагувати або видалити task
**Then** система відхиляє цю дію і показує viewer, що board доступна лише на перегляд

### AC-11 (US-06, US-07) — cross-context

**Given** team member щойно відкликав public link, яким раніше користувався viewer
**When** viewer, що зберіг старий лінк, намагається відкрити board за ним
**Then** система не показує стан board і повідомляє viewer, що доступ за цим лінком більше не надається

## 6. Non-functional requirements

| Aspect | Target | Measurement |
|---|---|---|
| Latency p95 запису (створення / редагування / переміщення / видалення task) | ≤ 300 ms | production monitoring |
| Latency p95 завантаження board (team member або viewer) | ≤ 500 ms | production monitoring |
| Throughput | ≥ 20 req/s на інстанс | smoke test у CI |
| Availability | 99% | щомісячне SLO-вікно |
| Узгодженість статусу task | task завжди належить рівно одній column, навіть при одночасному перетягуванні (last-write-wins) | domain invariant, AC-05/AC-05b |

## 6.1 Security / privacy

- **Data classification:** internal — назви task і вільнотекстові імена виконавців належать команді й не призначені для індексації чи публічного пошуку, навіть якщо команда свідомо ділиться ними через public link.
- **Personal data touched:** поле виконавця (assignee) — вільнотекстове ім'я, яке team member вводить сам; інших персональних даних система не збирає (акаунтів немає).
- **AuthZ/AuthN impact:** без входу в систему. Модель можливостей — рівно дві: «може редагувати» (доступ через інтерфейс редагування board) і «може лише дивитись» (доступ через public link); перевірок на рівні окремого користувача чи ролі немає.
- **Abuse cases:**
  - Витік public link у чат чи індекс пошуковика: після відкликання лінк ніколи більше не показує стан board, хай хто б за ним не звернувся (AC-11).
  - Спам-створення task: обмеження швидкості ≤30 створень task за хвилину з одного клієнта.
  - Ін'єкція через текстові поля task (назва, виконавець): система завжди зберігає й показує їх як буквальний текст, ніколи не виконує і не інтерпретує вміст.
  - Вандалізм через витік лінка: сам public link — read-only, тож його витік дає лише перегляд, ніколи зміну board (AC-10). Але це не робить вандалізм неможливим: мутуючі ендпоінти редактора (`/api/v1/tasks*`, `/api/v1/board/*`) відкриті без жодного секрету — прийнятий ризик ADR-0001 («без акаунтів»), і будь-хто, хто дізнається адресу самого board, може його редагувати. Фактичний захист — невгадуваність URL борда плюс rate limit на створення task; спільний секрет на редакторських роутах відкладено (див. §8).
- **Security review:** Required — новий неавтентифікований публічний доступ до даних команди; ідея-бриф §10 називає це головним ризиком проєкту.

## 7. Metrics / KPIs

- **Частка змін статусу, зроблених перетягуванням, а не переписуванням деінде (наприклад у чаті)** — baseline: 0% (продукту ще нема), target: ≥80% протягом перших двох тижнів використання командою.
- **Частка відкриттів public link, які успішно показують поточний стан board з першої спроби** — baseline: 0% (не перевірено), target: ≥90%, виміряно наживо під час воркшопу.
- **Час від створення першої task до наявності робочого public link** — baseline: н/д (продукту ще нема), target: ≤5 хвилин.
