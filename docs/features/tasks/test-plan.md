# Test plan — tasks

Задача набуває опису, пріоритету, дедлайну й коментарів. Кожен acceptance criterion
спеки §5 мапиться тут щонайменше на один тест — до того, як цей тест написаний.

## Levels

| Level | Scope | Strategy (generic — no tool names) |
|---|---|---|
| Unit (domain) | Правила самої задачі й коментаря: межі довжини, закритий набір пріоритетів, необовʼязковий дедлайн. | Чисті доменні конструктори й сетери, без БД і без HTTP. |
| Unit (app) | Скоуп доступу й побічні ефекти use-case-ів: чужа дошка за токеном, broadcast після кожної мутації. | Ручні fake-и на consumer-side портах, як у решті модуля. |
| Integration | Нові HTTP-роути й персистенція проти справжньої залежності модуля. | Ефемерний реальний Postgres на suite (testcontainers-style) + роутер, зібраний як у проді. |
| Component (web) | Маркери на картці й детальна модалка — і редакторська, і глядацька. | Рендер компонента з мокнутим API-клієнтом. |
| E2E-through-UI | Наскрізний шлях: створити задачу → деталі → опис+пріоритет+дедлайн+коментар → маркери на картці → те саме глядачеві. | Реальний UI проти живого локального стека. |
| Contract | <!-- N/A: web — єдиний споживач контракту; інтеграційні тести вже пінять справжню форму відповіді (в т.ч. відсутність description у стані дошки). --> |
| Visual-regression | <!-- N/A: жодного числового чи специфікованого візуального інваріанта; «протермінований бейдж червоний» перевіряється component-тестом по токен-класу, не скріншотом. --> |
| Load | Ціль §6 «стан дошки не деградує від коментарів». | Сценарій навантаження на стан дошки з насіяними коментарями. |

## Edge cases / error paths

<!-- Кожен error/authorization AC уже має рядок вище (TSK-02, TSK-04, TSK-09, TSK-12, TSK-13). -->
<!-- Нижче — межові й відмовні випадки, які випливають зі спеки й моделі даних поза цими AC. -->

- `due_date` у тілі запиту не у форматі `YYYY-MM-DD` → 400 `validation.invalid_due_date`, задача без змін (не 500 від драйвера БД).
- HTML/скрипт в описі чи коментарі → зберігається і рендериться буквальним текстом, ніколи не виконується (spec §6.1).
- Публічний детальний GET не має віддавати нічого понад `TaskDetail` — жодного `board_id`, жодного `public_link`.
- Публічний детальний GET має жити в тирі 300/хв, а не 60/хв: 61-й запит за хвилину ще проходить, 301-й — ні (spec §6.1).
- Коментар до неіснуючої задачі → 404 `task.not_found`, а не порушення FK у 500.
- Стан дошки з задачею без коментарів → `comment_count: 0`, а не `null` і не відсутнє поле.
- Мутуючі методи під публічним токеном (`POST /public/{token}/tasks/{id}/comments`) не існують як маршрут — відмова маршрутизацією, не перевіркою в хендлері.

## Test data

- Seed: інлайнове створення рядків у тесті, без фабрик — конвенція модуля. Seed-дошка й
  три колонки приходять із міграцій 000007/000009, як і в тестах фічі board.
- Інтеграційна залежність: ефемерний реальний Postgres на suite (`dbtest.StartPostgres`),
  ніколи не мок сховища.
- Дати в тестах дедлайну — відносні до `time.Now()` (вчора / завтра), ніколи не
  захардкоджений календарний день: інакше тест зеленіє лише до цієї дати.
- Межа кордону — рівно на межі й на один за нею: 4000/4001 символів опису, 2000/2001
  коментаря, 200/201 автора.

## NFR validation (load)

- Стан дошки на 100 задач × 20 коментарів → час відповіді не деградує проти тієї ж дошки
  без коментарів (лічильник має лишатись одним агрегатним запитом на колонку, а не
  запитом на задачу).
- p95 відкриття деталей задачі ≤ 500 ms (spec §6).

## CI placement

- На кожен PR: unit (domain + app) і integration — там живе коректність кожного AC.
- На кожен PR: web-unit (маркери картки, обидві модалки).
- На кожен PR: e2e-through-UI наскрізний сценарій деталей — він єдиний покриває звʼязку
  «редактор змінив → глядач побачив».
- За розкладом / перед релізом: load-сценарії.
